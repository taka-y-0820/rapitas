# Rapitas 自律開発・自己改善監査

調査日: 2026-09-06。対象: develop の 7e4c56de を基点とする実装、稼働中ローカルAPI、隔離worktreeでのテスト。既存の未コミット変更は保持した。

## 結論

**修正前58/100、今回の修正後62/100。** これは独自の設計成熟度ルーブリックによる判断であり、タスク成功確率でも、外部ベンチマークの点数でもない。全ファイル・全実行経路の監査ではなく、実行、検証、PR、回復、知識利用、プロンプト進化、評価の主要経路を重点調査した。実運用の改善効果は今回未測定。

既に「観測→失敗分析→改善候補生成→承認→注入」の部品はある。しかし「改善したという仮説→独立した比較評価→採用→悪化時ロールバック」の閉じた実証ループには不足がある。モデルの追加やプロンプトの増量より、正しい成果判定と評価用データを先に整備すべき。

## 採点方法

各項目は、未実装=0%、実装のみ=約40%、対象テストで裏づけ=約60%、統合・障害系で裏づけ=約80%、代表的実運用で継続測定=100%を目安にした専門判断。配点内の細部はリスクの重大性を加味しており、統計的な信頼区間を持つ数値ではない。旧来のアプリ機能充実度の評価とは基準が異なる。

## 稼働中APIで確認した事実

読み取りのみ実施。DB変更、実エージェント起動、PR作成、サーバー再起動はしていない。

- GET /learning/stats: totalExperiments=351、successRate=0.9373219373219374、promptImprovements=24、recentLearnings=[]。
- getLearningStats（rapitas-backend/services/self-learning/stats-ops.ts）では successRate は completed実験数/全実験数。351件中329件の完了に相当するが、受入条件の達成率・merge後の不具合率ではない。
- 同じ関数の promptImprovements は PromptEvolution の全件数。効果が確認された改善件数ではない。
- GET /learning/prompt-evolution/summary のスナップショット:

| ロール        | 総数 | APIのpendingCount | completedCount | 平均改善幅 |
| ------------- | ---: | ----------------: | -------------: | ---------- |
| auto_verifier |    3 |                 3 |              0 | null       |
| verifier      |    6 |                 6 |              0 | null       |
| implementer   |    6 |                 6 |              0 | null       |
| planner       |    3 |                 3 |              0 | null       |
| researcher    |    6 |                 6 |              0 | null       |

注意: prompt-ops.ts の pendingCount は「statusがcompleted以外」の全件。proposed、approved、rejectedなどもこの集計に含まれ得るため、24件すべてが文字どおりpending、または承認済み0件とは断定できない。workerはapprovedを注入対象にするため、completedだけを見る集計には状態語彙の不整合もある。

上位パターンにはPR mergeコマンド失敗58回、状態不整合47回、verify_validation_failed反復43回が記録されていた。これはパターン出現回数であり、ユニーク失敗タスク数でも、現在も未修正という証拠でもない。優先的な再現ケース収集に使うべき。

## 今回の修正

1. verification-gate.ts: 検証器の例外をok:true/nullで返す処理を廃止。ok:false/unverifiable:trueでブロックし、セッションに検証環境の問題と記録する。コードの欠陥と断定しない。詳細例外はサーバーログに保持する。
2. post-execution-review.ts: 別経路にも同じ例外時の通過処理があったため、共通のverificationCrashResultを使用。既存retryOrBlockのunverifiable分岐で停止し、AIレビュー・commit・PRへ進まない。
3. prompt-evolution-runner.ts: completed/failedだけを評価対象にし、進行中・待機中・キャンセルを分母から除外。ゲート差し戻し履歴の取得失敗は評価スキップとし、プロセス終了状態だけで学習候補を作らない。
4. 回帰テスト: 検証器クラッシュ、セッションなし、検証不能時の再実装抑止、非終端状態の除外、実際の失敗からの候補生成、学習用証拠の取得失敗を確認。

スキーマ変更なし。サーバーは再起動していないため、稼働プロセスへの反映有無は起動方式次第。停止要求と検証失敗の同時発生を含む全経路の競合安全性まで保証する修正ではない。

## 残る改善の優先順位

### P0: 成功の定義を一本化

- process_completed、verification_passed、pr_created、merged、acceptedを別イベントにする。
- 完了条件はタスクの設定から決め、要求された最後の段階の外部証跡が存在する時だけ成功にする。
- 証跡にtaskId、attemptId、commit SHA、base SHA、test command/exit code、PR URL、merge SHA、モデル実名、prompt/knowledge versionを記録する。
- 検証結果を特定のSHAへ結び付ける。検証後にbase取り込みや編集が発生したら再検証する。
- APIのsuccessRateを廃止する前に後方互換の明示的なcompletionRate、acceptedTaskRate、sampleCount、window、unknownCountを追加する。
- 受入条件: 検証不能・PR未作成・CI未確定・キャンセルではacceptedにならない。再起動後も同じ結果になる。

### P0: 「判定不能」を成功にしない公開方針

verification-gate.tsのindeterminate triageは既存仕様として懸念登録だけで通過する。automated-verifier.tsではscope/acceptanceも助言扱いで、単語一致の受入自己チェックは意味的な動作保証ではない。
一律に停止へ変更すると既存運用を大きく変えるため今回は未変更。PRのdraft作成までは許可しても、自動merge・acceptedは独立したCI検証か人の承認を必要とする三値判定(pass/fail/unknown)を推奨する。

### P1: Rapitas専用の非公開評価セット

- 過去の実タスクからバグ修正、機能追加、調査のみ、複数サービス変更、失敗復旧を分けて収集する。
- 初期30～50件は運用開始の目安で、統計的な十分性の保証ではない。同じ課題を複数回実行し、必要件数は検出したい改善差とばらつきから決める。
- 学習用課題と評価用課題を分離し、受入テストを実装エージェントに変更させない。
- fail-to-passと既存動作のpass-to-passを両方測る。実UI/API、DB、CLIスタブ子プロセス、使い捨てGitリモートを含むE2Eを別DBで実行する。
- 故障注入: 停止直後のCLI終了、検証中の停止、DB書込失敗、二重callback、PR作成成功後の応答喪失、CI失敗、プロセス再起動。
- 指標: 初回受入率、最終受入率、誤完了率、人の介入率、再修正回数、停止完了p95、成功1件あたり費用・時間、merge後の回帰率。
- 既存eval-gates.tsは決定的な関数評価であり、これの代替にはならない。

### P1: 改善候補の比較評価と段階採用

- 同一モデル・同一予算・同一課題で現行版と候補版を対比較する。知識あり/なしも比較し、タスク難度・モデル変更の影響を分ける。
- 成功率だけでなく費用と所要時間も評価し、改善差と不確実性を保存する。5サンプル・70%閾値は候補生成のトリガーに留め、採用証明にしない。
- 基盤障害、ユーザーキャンセル、実装誤りを別ラベルにする。今回の修正でもfailedの内部原因分離、同一タスク内の試行単位での帰責は未実装。
- 合格した候補だけ少数タスクに適用。品質・費用悪化で前版へ戻せるようプロンプトと知識の版を固定する。
- 人の承認は外さない。自動評価の信頼性が確認できてから、低リスク変更だけ自動採用する。

### P1: 反復停止を「安いモデルへ変更」だけに頼らない

task-budget.tsは支出超過でtierを下げる設計で、厳密な停止予算ではない。参照失敗時も0扱いになる。
時間・費用・試行回数・同一原因の反復をタスク全体で管理し、進展がない場合は「新しい仮説が必要」と停止する。終了条件・再開条件を記録し、ユーザー停止と自動回復が競合しない実行世代IDを使う。

### P2: 知識の評価を量から効用へ

effectiveness.tsは注入した知識の利用率・成功率を集計するが、対照群はない。取得失敗もゼロ集計となる。outcome-reinforcement.tsの報酬付与も、宣言がない場合は注入全体へ帰属し得る。
出典・適用条件・版・有効期限・反証を保持し、誤知識を隔離する。障害時は0ではなくunknownを返す。知識の増加件数を賢さと呼ばない。

## 外部の実証・方法論

- [UTBoost, ACL 2025](https://arxiv.org/abs/2506.09289): 不十分なテストを持つ36課題を特定し、元の評価で合格とされた誤パッチ345件を検出。既存テスト合格だけで「問題解決」と見なさない根拠。Rapitasの誤り率を示す数字ではない。
- [A Self-Improving Coding Agent, 2025](https://arxiv.org/abs/2504.15228): SWE-bench Verifiedのランダム部分集合で17%から53%への改善を報告。自己改変の可能性を示すが、全ベンチマークやRapitasで同じ改善が出るという保証ではない。
- [Anthropic: Demystifying evals for AI agents, 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents): 発言や実行履歴と環境上の成果を分け、複数試行・コード評価・人による評価の校正を組み合わせる。Rapitasではログ件数と完了フラグから独立した受入評価への移行に対応する。
